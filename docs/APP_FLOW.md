# App Flow

How the app turns a job posting url into a tailored resume and cover letter, and how base resumes are kept. Every suggestion follows [WRITING_RULES.md](WRITING_RULES.md). Content comes from the database described in [DATABASE.md](DATABASE.md).

## Modes
The app has distinct modes, so it's always clear whether the user is managing their content or building a document. Home asks "What do you want to do?" and offers one choice per mode; the main nav lists them too (`frontend/src/modes.ts`).
- **Library** (`/library`): view and edit everything a resume or cover letter can draw from (headers, sections, skills, experience, projects, bullet points, and the rest), with its own sub-nav. Each page lists its cards A to Z, and says so, with hidden items last under "Hidden (n)", closed to start, each with Unhide. Each item is a card showing its title, a short summary, and View and Edit, which opens the item's dialog: its form (Save), then Hide and Delete, then its lists, the sections that list it, and what uses it. Hide sets an item aside: it isn't offered anywhere new, but whatever uses it keeps it. An item a sent application uses offers Hide in place of Delete. A section's dialog shows only its default kind and the kinds it lists, with the rest under "More options". Delete opens in place of the form, never as a second dialog. Every kind changes the same way: when resumes or cover letters in progress use the item, a note above its fields says what Save will do, and checkboxes list them, none checked to start; the ones left unchecked keep the item as it is, and sent ones never change (see "Changing an item" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). There's no "New version": to keep two wordings side by side, the user writes the second as new content. Saving and deleting close the dialog; changing a list keeps it open. A name inside the dialog (a bullet under a role, the role or section that lists a bullet, a category's skills) shows that item in the same dialog, with "Back to [the item before]", and Close or Escape closes it from any depth, and focus stays inside it while it's open. Names of resumes, cover letters, and postings under "Used by" link to their pages.
- **Job postings** (`/postings`), **Resumes** (`/resumes`), and **Cover letters** (`/cover-letters`): create and work on them, following the user flow below. A job posting has its own page (`/postings/:id`), headed "[role title] at [organization] Application": its link (opening in a new tab) and job description (closed until opened, with Edit details and Delete inside it), its header (open until it's picked, then closed), its resume and cover letter (links named "Resume" and "Cover letter"), each started one of five ways: tailored by Claude (the default, with a tone), a copy of any earlier one as is, built from scratch (empty), or an uploaded file or pasted text of the user's own (see "Starting from an existing resume or cover letter" below, and "Starting a version for a posting" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)), and its "Application tracking" (closed until opened): the dates and contacts, with Edit tracking, and its interviews. A new posting starts from its link (or its primary contact, when it has no posting online): "Read posting" has Claude read the page, or the description pasted in ("Paste the description", which opens on its own when the page can't be read), and fills in the organization, role title, and description for the user to check and correct before "Save posting" (see "Reading the job posting" below). "Fill in by hand" skips Claude. A new posting opens on its page to pick its header first, from the suggestion. A resume or cover letter has its own page (`/resumes/:id`, `/cover-letters/:id`) where it's built in place, with no separate details form:
  - Its title: a base version's ends in "Base Resume" (or "Base Cover Letter"), and one for a posting's in "Resume" (or "Cover Letter"). Then a short note on what editing does, then Copy and Delete (a sent version: Copy and Hide, or Unhide, since it can't be deleted).
  - Under the Contents heading, before the tone: "Title", the title, and "New title", which opens a modal to type the name (with the suffix the app adds shown beside it), Save or Cancel. Saving closes it and says so; focus goes back to "New title".
  - Its tone, at the top, with **Undo** and **Redo**: every change made on the page can be undone one step at a time, back to when it was opened, and redone (see "Undo" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). Anything written to the library stays there.
  - A tree of nested lists whose levels open and close (the disclosure pattern), all starting closed, so the user can work on one part at a time with everything on one page:
    - **Header:** each value (name, headline, email, phone, location, LinkedIn, GitHub, portfolio) is shown under its name, then a "More [value] options" dropdown (when there's anything else to pick) offers every other value saved in any header and none (except for the name), applied right away, and a "New [value]" button opens a small modal to type one in, starting with the current value so it can be tweaked (empty for none); its Apply puts it in the form, and applying it unchanged changes nothing. A screen reader hears each change ("Location changed to Boston, MA"). Nothing saves until "Save header", which points the document at the saved header with exactly those values, or a new one, so trying combinations out never adds headers. "Undo changes" goes back to the saved values. A version for a posting shows its "Application header" (the posting's) instead, with a link to change it there.
    - **Sections:** add, remove, and reorder them. Each section opens to its items (any mix of kinds, in one order). A role, project, or education entry opens to its fields; a category or project to its skills; and a role or project to its bullets. An item with more than one of these (a role or project) shows each as its own level, "Details", "Skills (n)", and "Bullets (n)", also starting closed; one with only one (a category's skills, an education entry's fields) shows it right away.
    - **Defaults, then More options:** every level starts filled with defaults (a posting's document started with Claude starts from Claude's draft instead): a new resume or cover letter gets default sections, an added section its default items, and an added role, project, or category its default bullets and skills (see "Defaults" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). Under each list, a "More options" level (closed to start) offers the rest of what the library lists there as checkboxes: a section's items (grouped by type), a role's or project's bullets, a category's or project's skills, and for the sections list, every section. The user checks any number and clicks Add; they go last, and a section's items come with their own defaults. When everything listed there is already shown, it says "No more options" in the same place. Remove, reorder, View and Edit, New bullet (under a role or project), and New skill (under a category or project) work alongside it.
    - **Adding other content to a section** ("Add content", named for its section for screen readers, inside the section's "More options", which starts open for an empty section) is type first: pick the type (role, project, skill category, education, bullet, or narrative content), then a saved item of that type (the ones the section lists first), or "New …" (first, before the saved items) to fill in that type's fields, which saves it to the library under the section. A saved item comes with its defaults. In a cover letter, the type starts as narrative content. In a resume, it starts as the kind the library lists most under the section, never decided from its title; a section that lists nothing asks for the type. An empty section shows this form right away.
    - **View and Edit** on every row (a section, a role, project, education entry, skill category, skill, bullet, or narrative content) opens the item's dialog, the same one the library shows. Saving there changes the item in this document without asking, and the form asks only about the other resumes and cover letters in progress ("Saving changes it in this resume only." when there are none). When that saves a new library item, listed right after the original wherever the original is listed, this document switches to it, keeping what's under it, and the original stays in the library and in the other documents. Nothing changed saves nothing (see "Changing an item" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). Closing the dialog returns focus to the row.
    - **Greeting** and **Sign-off** (cover letters only).
  - **Preview and copy:** the plain-text output, with copy buttons, as one more level that opens and closes (its button is a heading, so it's found by heading).

  Changes save as they're made: a choice from a dropdown right away (the tone, the sign-off), and typed text (the greeting, the name under the sign-off) when the user leaves the field or presses Enter. The header saves with "Save header", since each combination of its values is a saved header. Checked options save with Add, and forms that start something new (adding content to a section, a new bullet or skill, renaming) save with their own button.

  A base version, and one for a posting until it's sent, is edited in place right away; the note says edits save instantly, Undo and Redo work only while the page is open, and Copy keeps this version as it is (see "Editing in place" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). A sent version shows the tree read-only and can only be renamed. The Resumes and Cover letters pages list hidden ones last, under "Hidden (n)", closed to start, each with Unhide.

Building a resume or cover letter never requires switching to the library: content written there (a new or reworded bullet, new narrative content, a new section from "New section title" inside the Sections' More options, a letter's new sign-off) is saved to the library as part of the flow.

## Reading the job posting
1. Fetch the HTML from the url.
2. Find the part of the page that holds the job description. Ignore navigation, ads, and unrelated listings.
3. Pull out its text, including any description of the organization, its mission, and its values. Those are used for the cover letter and for tone.
4. Show the extracted text to the user so they can fix anything that was missed or picked up by mistake. Nothing is saved until they save the posting.

Pasted text skips the fetch: Claude pulls the organization, role title, and description out of it the same way, and when it finds no job description in it, the pasted text is kept as the description, for the user to fill in the rest.

If the page can't be fetched (many job sites block automated requests) or no job description is found, the app shows a box for pasting in the job description instead (`POSTING_FETCH_FAILED`, see [API_ERRORS.md](API_ERRORS.md)). If a Claude request fails at any step, the user's work so far is kept and they can retry (`AI_UNAVAILABLE`).

## Starting from an existing resume or cover letter
Any new resume or cover letter, base or for a posting, can start from one the user already has: an uploaded PDF or Word (.docx) file, or its text pasted in. The library fills itself this way instead of being typed in, the same idea as `/seed-resume`.
1. **Claude reads it** into sections and library items (narrative content one sentence per item, bullets, roles, projects, skill categories with their skills, education), plus the header, and for a cover letter the greeting, sign-off, and name under it. Each paragraph of a letter is its own section, titled with a short label for what it does, reusing a library section's title where it plays the same role. Text is copied exactly as written, except headings and titles in all capitals only for styling.
2. **Each item is matched against the library.** An identical one is reused, not added again. Where Claude sees a library item that looks like the same thing written differently ("Acme Corp" and "Acme Corporation", the same role with other dates), it's named beside the item, for the user to choose.
3. **The user checks it** in a form where they started: each section and item with its fields to correct and Remove, the new ones marked "new", and "Use the saved one" (and back) where Claude saw a similar library item. Reordering and adding happen afterward in the usual tree. Nothing is saved until Save; leaving loses the reading, and the user reads it again.
4. **Save** adds the new items to the library, each listed under its section, category, role, or project, and creates the document with them. A base one uses the header read from it (the saved one with the same values, or a new one). One for a posting uses the posting's header, and the user chooses each time: "Save as is" (one already sent or finished elsewhere), or "Save, then Claude tailors it", which has Claude tailor it to the posting from there, through the same draft review as "Tailoring a posting's document".

## User flow
Everything for an application hangs off its job posting. A resume and a cover letter aren't linked to each other directly; both belong to the posting and share its header.

1. **Create the job posting.** The user enters the url. The app extracts the job description as described above and saves it as a `job_posting` with the organization and role title.
2. **Choose the header.** The posting's header (`job_posting.header_id`) is the user's header for their application, not the posting's. The app suggests a header: the user's name and contact details from their most recent header, with a headline (the role title shown under their name) based on the posting. The user accepts it, edits it, or picks another saved header. A changed headline or contact detail is saved as a new header, so earlier resumes and cover letters keep theirs. The choice is saved as the posting's header, which all its resumes and cover letters use. It's changed only on the posting, and the change reaches all of them.
3. **Start a resume or cover letter for the posting.** Either can come first. A posting has one of each, worked on in place until the user applies. Each uses the posting's header, which is changed only on the posting, and is named for the posting. By default Claude tailors it (see "Tailoring a posting's document" below): it starts from the saved version, base or tailored, that fits the posting best, or one the user picks on the Start form ("Start from"), and the user reviews the draft. The user can instead copy a saved one as is, which keeps its sections and selections (and tone) ready to adjust, build from scratch, with no sections, or start from their own file or pasted text (see "Starting from an existing resume or cover letter" below), which they save as is or have Claude tailor from there. Every way but a copy takes a tone, if any, picked on the Start form, since Claude writes in it. Either way the result is saved as a new version linked to this posting, and the original is not changed.
4. **Choose sections.** Steps 4 and 5 work in whatever order the user likes (see "Working in any order" below). Claude's draft suggests which sections to include and in what order (see "Tailoring a posting's document" below). Usually that's all of them, but it may leave some out, such as freelance experience or projects, when they don't fit the job. The user can add, remove, or reorder sections.
5. **Build each section.** Claude's draft suggests the content for every section at once, and afterward "Ask Claude" on a section or item asks for more (see "Working with Claude at every level" below):
   - **Summary / narrative content:** which existing narrative content (sentences or whole paragraphs) to use, and in what order
   - **Skills:** which skill categories and skills to include, and their order
   - **Experience:** which roles to include and which bullet points for each, chosen from all the bullets listed under that role: the ones that best fit the posting, leaving out near-duplicates of each other
   - **Projects:** which projects to include, which of their skills to show, and which bullet points to use, chosen the same way
   - **Education:** which entries to include

   For each suggestion the user can:
   - accept it
   - swap a bullet for another one listed under the same role or project
   - ask for a variation of a bullet, or write a new one; either is saved as a new bullet listed under that role or project
   - ask the app for further tweaks
   - make their own edits or describe their own ideas for the app to work from

   Any section can be taken up again in the chat, at any time, for more suggestions like these.

   **Working in any order.** The user decides how to build the resume, and can switch approaches at any time:
   - lay out all the sections first, then go back and fill each one
   - go section by section from the start, choosing content as each section is added
   - add sections in any order, reorder them, and remove them at any point

   Nothing is final until the user is done: any section's content, the section order, the header, and the tone can all be changed until then. The cover letter works the same way. Once the user records the date they applied, the posting's resume and cover letter are locked as a record of what was sent; later changes go in a copy.
6. **Build the cover letter.** It follows the same steps under the same posting: header, starting point, sections, then choose, order, and adjust each section's content (usually narrative content, but any kind of content the user wants). Each paragraph is a section. When the user writes a new paragraph, the app suggests a short title from its content (e.g. "intro", "key technical demands"), reusing an existing section when the paragraph plays the same role. The user can change it. Titles are never printed in the letter. The app sets the greeting ("Dear [organization] Hiring Team,") and the sign-off ("Sincerely," and the user's name), and the user can change either. When Claude tailors the letter, it also suggests the greeting when the posting names who is hiring, and writes new paragraphs from the posting (see "Tailoring a posting's document").
7. **Review the whole thing.** The app reviews the posting's finished resume and cover letter together. It checks how well they cover the job's keywords, and looks for repeated wording, inconsistencies, and anything that breaks the writing rules.
8. **Output** the final resume and cover letter as plain text for the user to copy and paste into their own document or an application form. There are copy buttons for the whole document and for each section. No .docx or PDF export for now; the user wants PDF (and maybe .docx) downloads eventually (question 26 in [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md)).

   Plain-text layout:
   - **Header:** name, then the headline, then contact details and links on one line separated by ` | ` (email, phone, location, then the LinkedIn, GitHub, and portfolio links).
   - **Resume sections:** the section title, then its content, with a blank line between sections.
   - **Narrative content:** excerpts placed one after another run together as one paragraph.
   - **Skills:** one line per category, like `Category: skill, skill, skill`.
   - **Experience:** `Role Title | Organization | Location | Dates`, then its bullets.
   - **Projects:** `Project Title | Done For | Dates`, then a `Skills: skill, skill` line and its bullets.
   - **Education:** `Degree | Institution | Graduation`, then its details.
   - Empty parts of a line (nothing in `done_for`, no dates) are left out.
   - **Bullets:** each starts with `- `.
   - **Cover letter:** header, greeting, paragraphs separated by blank lines (no section titles), then the sign-off and the user's name (the letter's `signature_name`, or the header's `full_name` when that's empty). No greeting without an addressee, and no closing without a sign-off.

   The backend builds the text (`backend/app/plain_text.py`) in parts: the header, each section, and a letter's greeting and sign-off, so each part has its own copy button.
9. **Track the application.** On the job posting, the user can record the date they applied (which locks its resume and cover letter), the date they were turned down or hired, and contacts such as the hiring manager or a referral. All of it can change at any time, and clearing the applied date asks first, since it unlocks them. They can add interviews (date and notes), and link one interview to several of the organization's postings when it covered more than one opening; the form offers the organization's other postings, matched ignoring capitals. An interview shows on every posting it covers and can be changed from any of them.

## Base resumes
Base resumes and cover letters aren't tied to a job posting. They're ongoing starting points the user keeps coming back to, such as a general tech resume or a teaching resume. The seeded data starts out as base resumes.
- The user can create, edit, and improve a base resume at any time, without a url. The same section-by-section building, suggestions, and writing rules apply, just without a posting to match against.
- Edits to a base resume change it directly, as they're made. They don't create a new version, and once the page is closed the earlier state can't be recovered (Undo works only while it's open). A note above Copy says so, and Copy makes a new base resume based on this one, so the original stays available.
- A tailored version that turned out well can be copied into a new base resume, from its page or by picking it under "Start from" when creating a new base resume.
- A new base resume or cover letter starts fresh (with the defaults), as a copy, or from the user's own file or pasted text (see "Starting from an existing resume or cover letter").

## Suggestions
Suggestions are based on:
- **Keyword matching:** skills, tools, qualifications, and values named in the posting, compared against the content in the database.
- **AI judgment:** the same kind of review an AI does when asked in chat to tailor a resume. That includes relevance to the role, strength of results and impact, mirroring the posting's language where it's accurate, and order (strongest match first).

**Tailoring a posting's document** (phase 5; see step 2 in [BUILD_PLAN.md](BUILD_PLAN.md)): one Claude request when the document is started. Claude picks the saved resume (or cover letter) that fits the posting best as the starting point, or starts from the one the user chose, swaps items that don't match well for better ones from the library, then makes minimal tweaks to align the content with the posting, following the writing rules and the document's tone, with a reason for each choice. When the posting already has the other document (its resume, for a cover letter, or its cover letter, for a resume), Claude reads it too and keeps the two consistent: the letter expands on what the resume shows without repeating its bullets, and the resume backs up what the letter claims. The chat reads it the same way, each time it changes. Either way it looks through the whole library for better items, and its reply is the whole document, including what it keeps as is. The document is created empty, with the result as its draft, in the same request, so if Claude fails nothing is created and the Start form offers to try again. The draft takes the tree's place on the document's page, with the Sections level open: where Claude started from and why, then every section, item, bullet, and skill in Claude's order. The first pass is only for accepting or rejecting Claude's suggestions, so suggestions the user discards don't clutter the library. Each row has a badge: "Original" (in the document Claude started from), "Library" (brought in from the library), or "Claude" (Claude's wording or new text). Under each, "Rationale" opens Claude's reason, whether it kept the item, brought it in, or reworded it, and for a rewording, the original with "Use the original" (or back again, Claude's suggestion with "Use Claude's wording"). Before the draft is shown, its text is checked against the writing rules: Claude's wording is fixed where it breaks one, and what's still flagged (and any library item's own wording that breaks one) is marked "Flagged" with the rule and why, for the user to decide. If the check itself fails, the draft is shown anyway, saying its writing wasn't checked, with "Check writing rules again", which runs only the check. What's marked "Library" and Claude's new text have "Reject", which takes them out of the draft. Each change saves the draft only, with Undo and Redo. Reordering, adding, writing new content, and View and Edit come after approving, when the user fine-tunes the whole document with Claude. "Approve first draft" first asks which of Claude's texts the draft doesn't use to keep in the library for later (none checked to start; the rest are discarded), then saves what the user kept: Claude's kept wordings become new library rows, listed right after their originals (new text under the section, role, or project Claude put it in), used in this document only, and the document is based on the one Claude started from. Approving can't be undone, so the page's history starts again.

For a cover letter, Claude also writes new paragraphs from the posting where the letter needs one the library doesn't have, such as why this organization (from what the posting says about it) or how the person's experience meets its main requirements, with every claim about the person backed by the library. Each sentence is its own narrative content item. A new paragraph goes in the library section that plays the same role, or in a new section Claude titles, which is badged "Claude" and can be rejected; it's added to the library only if it's kept. And when the posting, or the user's contacts notes on it, names who is hiring, Claude suggests greeting them by that name as written, never guessing a title such as Ms. While the draft has Claude's greeting, the letter's Greeting level shows it in place of its field, badged "Claude", with its reason and "Use the usual greeting"; approving saves the one in use.

**Working with Claude at every level** (phase 5; see sub-step 4 in [BUILD_PLAN.md](BUILD_PLAN.md)): there's no "Suggest again"; instead, one chat panel beside the document, opened from "Ask Claude" on the whole document, a section, or an item, lets the user workshop the document with Claude ("tweak this bullet to better match the posting's keywords"). A bullet's or narrative content's dialog, opened from a row, has its own "Ask Claude" section, so the user can ask about an edit without leaving it: the question goes with the unsaved text, and "Use this" on Claude's wording puts it in the field, saved with the dialog's Save. That exchange joins the same conversation. Each resume and cover letter keeps its whole conversation, shown when the user comes back and read by Claude each time, so it builds on itself; a copy doesn't copy it. Base versions and a posting's unsent ones have the chat, after any first draft is approved; a sent one shows its conversation read-only. Each message says what it's about (the document, a section, or an item). Claude's reply appears as it's written, and a screen reader hears "Claude is replying", then the whole reply once it's done. Claude's proposals can be text never used before, not just items already in the library: rewording, adding, removing, or moving a section, an item, a skill, or a bullet. Anything the user could do on the page, Claude can propose, such as showing any skill under a skill category or project, or a new skill, instead of sending the user to the library. Each shows as a card with its before and after, naming where it is by its immediate parent (the skill category, role, or project, or the section), and folds its details away once it's applied or dismissed; nothing is changed until the user applies one, and Claude is told in the next message which ones the user applied or dismissed. Before the cards are shown, their text is checked against the writing rules, as the draft's is: Claude's wording is fixed where it breaks one, and what's still flagged (and a saved item's own wording it adds as is) is marked "Flagged" with the rule and why, on the card and on Claude's wording in an item's dialog. The panel says while it's checking, and the reply's announcement says how many changes are flagged. Claude is told in the next message about each fix and what's still flagged. If the check itself fails, the reply is kept, saying its changes weren't checked, with "Check writing rules again", which runs only the check on the ones not applied yet. A card stays until the user applies or dismisses it, and the panel lists the ones still waiting above its message box ("Waiting for you"), each going to its card, so one asked about earlier isn't lost up the conversation.

Beyond choosing existing content, the app also suggests improvements, such as rewording a bullet point, reordering skills, or rephrasing part of the cover letter. When the user accepts a reworded or new bullet point, it's saved as a new `bullet_point` row linked to the same section, experience, or project. Accepted reworded or new narrative content (in a summary or cover letter) is saved the same way, as a new `narrative_content` row linked to the same section. Either way the new row can be reused later, takes the original's place in the current resume or cover letter, and the original stays in the library.
