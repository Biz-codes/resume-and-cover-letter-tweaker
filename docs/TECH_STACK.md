# Tech Stack

| Layer     | Choice                                             |
|-----------|----------------------------------------------------|
| Backend   | Python with FastAPI                                |
| Database  | PostgreSQL 18, installed locally with Homebrew     |
| ORM       | SQLAlchemy, with Alembic for migrations            |
| Front end | React with TypeScript, built with Vite             |
| AI        | Claude Opus 5.5 through the `anthropic` Python SDK |
| Hosting   | Runs locally on the user's machine                 |

## Why
- **FastAPI:** a lightweight API framework for a separate React front end. It handles slow calls (fetching job postings, AI requests) well and generates API docs automatically.
- **SQLAlchemy + Alembic:** the standard Python tools for working with Postgres and tracking schema changes as migrations. The schema in [DATABASE.md](DATABASE.md) maps to SQLAlchemy models.
- **TypeScript:** resumes are deeply nested (resume → sections → items → skills and bullets). Types catch mismatches between the front end and the API early.
- **Local:** no hosting cost, the user's resume data stays on their machine, and no login system is needed. It can be deployed later if that changes.

## Project layout and tooling
- `backend/`: FastAPI app, SQLAlchemy models, Alembic migrations, tests. Python packages in a `venv` installed with pip.
- `frontend/`: Vite + React + TypeScript app. `frontend/src/` is grouped by feature: `library/`, `postings/`, and `documents/` (resumes and cover letters) each hold their pages, components, and API modules, and `shared/` holds what more than one feature uses (`shared/api/`, `shared/components/`, `shared/hooks/`). A file used by one feature goes in that feature; once another feature uses it, it moves to `shared/`. `App.tsx`, `main.tsx`, `modes.ts`, `HomePage.tsx`, `index.css`, and `test/` stay at the top. A component's `.tsx` and `.test.tsx` sit side by side; one with a third file (its `Name.module.css`) gets its own folder, such as `shared/components/OrderedList/`.
- **Styles:** `frontend/src/index.css` holds what's site-wide: the colors (as variables on `:root` too, such as `--border`), base element styles, layout and breakpoints, and classes several components use (`muted`, `tag`, `actions`, `card`, `visually-hidden`, and the like). Styles only one component uses go in its `Name.module.css`, read as `styles.camelCaseName`, and use the color variables, never their own colors, so the contrast check covers every color (see "Accessibility" below). Tests see the modules' plain class names (`vite.config.ts`).
- `db/`: seed SQL files (`seed_defaults.sql` and `seed_helpers.sql` committed; `seed_personal/`, one file per resume, gitignored).
- **Tests:** pytest for the backend, Vitest for the front end.
- **Linting:** ruff (Python), and tsc and oxlint (TypeScript, including oxlint's jsx-a11y accessibility rules), run automatically by a Claude Code hook after each edit.
- **Accessibility:** the front end targets WCAG 2.2 AA. See "Accessibility" below.
- **Layout across screen sizes:** the CSS (`frontend/src/index.css`) is written for narrow screens first, and no page needs sideways scrolling down to 320px wide (WCAG 1.4.10). Site-wide breakpoints: small is under 640px (rows stack, spacing tightens), medium is 640px and up (the default), and large is 1024px and up (the page widens). Use these same numbers in every media query. Form controls never grow wider than their container.

## Running it
Postgres 18 runs as a Homebrew service on port 5433 (see [BUILD_PLAN.md](BUILD_PLAN.md)). From `backend/`:
- `.venv/bin/alembic upgrade head`: apply migrations to the app database
- `.venv/bin/uvicorn app.main:app --reload`: start the API on port 8000
- `.venv/bin/pytest`: run the backend tests (against `TEST_DATABASE_URL`, whose schema they rebuild)
- `.venv/bin/alembic revision --autogenerate -m "..."`: create a migration after changing `app/models.py`

From the project root:
- `scripts/check.sh`: run every check (backend lint, tests, and schema drift; front end types, lint, and tests). The git pre-commit hook runs it too.

From `frontend/`:
- `npm run dev`: start the app at http://localhost:5173 (it forwards `/api` to the backend)
- `npm test`: run the front end tests

### Commit messages
Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat: ...`, `fix: ...`) and describe only the staged changes. There are two ways to get one written, and both ask the commit's type (feat, fix, refactor, docs, or chore) and then the message's length (succinct, highlights, verbose, or write your own):
- **`git commit` in a terminal:** the `prepare-commit-msg` hook asks in the terminal, has Claude write the message, and opens the editor with it to review. It keeps only Claude's output from the first line starting with a commit type, since `claude -p` can print narration above the message; output with no such line counts as no message. Its suggested type comes from the staged files' paths alone, so it answers instantly: docs for docs only, chore for tooling only, feat when the app gains a new file, and no suggestion otherwise. It can't tell a fix from a refactor, or notice that a change to app code is really a fix.
- **`/commit-message` in Claude Code:** Claude reads the whole staged diff before asking, so its recommended type is an informed judgment. It shows the message for you to copy.

**For a better type recommendation, run `/commit-message` first.** Use its message, or note its recommended type and pick that at the hook's prompt. The hook's suggestion is fine when the staged files make the type obvious (only docs, or only tooling).

## API conventions
Every library table follows the pattern set by headers (`backend/app/routers/headers.py`, `frontend/src/library/HeadersPage.tsx`):
- **Routes** live under `/api`, one router module per table in `backend/app/routers/`: `GET /api/<items>` lists, `GET /api/<items>/{id}` gets one, `POST` creates (201), `PUT /api/<items>/{id}` replaces the editable fields, and `DELETE` removes (204).
- **The current account:** endpoints take `AccountId` from `backend/app/account.py`, which creates the account with its defaults on first use. Look items up with `get_owned`, which returns `NOT_FOUND` for missing items and for other accounts' items alike.
- **Input:** request bodies use the field types in `backend/app/schemas.py`: text is trimmed, blank optional fields are saved as empty (null), and lengths match the columns, so bad input returns `VALIDATION_FAILED` naming the field.
- **Responses** include what the delete warning needs (e.g. `used_by`, with `locked` for sent versions), so the page doesn't need extra requests. `backend/app/usage.py` finds the resumes and cover letters that use an item, through each join table that can reach it, or through their own column for a tone set or sign-off (`column_uses`).
- **Names and lists:** `backend/app/library.py` checks unique names and the ids sent in a list, and edits a parent's ordered list of children (`PUT /api/<items>/{id}/<children>` replaces the whole list, in order). Built-in parents are shared, so their lists are always narrowed to the current account's children. `backend/app/refs.py` reads a list from either end (a role's bullets, the sections that list a role) as short refs for responses.
- **Built-in rows:** refer to the built-in sections and "Other" by their fixed ids, never by title: the constants in `backend/app/models.py`, and in the front end `BUILT_IN_SECTION_IDS` (`frontend/src/shared/api/sections.ts`) and `OTHER_CATEGORY_ID` (`frontend/src/shared/api/skills.ts`).
- **Item versions:** every library kind has `POST /api/<items>/{id}/versions`, which adds a version listed like the original and sharing its lists (see "Versions in the library" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)). Each kind's router has a `new_version` helper that adds the row and lists it, which its versions endpoint, its edits that save a new row, and the resume and cover letter tree's "New version" share. Roles' and projects' `PUT` takes `apply_to_unsent` (the user's answer to whether resumes and cover letters in progress get the change; see "Changing a role or project" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)).
- **Versions:** a write that would change a sent version saves a new row instead (see "Sent versions are locked" in [FRONTEND_CHECKS.md](FRONTEND_CHECKS.md)); the response is the row that was saved, so a different id tells the page a new row was made. `backend/app/versions.py` has the lock condition, and `switch_unsent` in `usage.py` moves unsent versions to the new row.
- **Resumes and cover letters:** their join tables mirror each other, so `backend/app/documents.py` describes each kind's tables once (`RESUME`, `COVER_LETTER`), and the same code reads a document's tree (`load_tree`) and copies it (`copy_tree`). `/api/resumes` and `/api/cover-letters` take the same requests, and a document's `GET` includes its tree (`sections`, with each join row's `row_id`) and its plain-text output. `backend/app/routers/document_tree.py` adds the endpoints that build the header and tree to both routers (`add_tree_routes`): the header's values (finding or adding the header with exactly those values), and each list in its new order (sections, a section's items of any kind, an item's skills or bullets), keeping the rows that stay, writing new items in place (including a new section, and a letter's new sign-off), new versions at every level (`.../version` for a section, an item, or a skill, and `replaces` for text), and the whole tree at once (`PUT .../tree`, which undo and redo send); each returns the document. Creating a document, adding a section, and placing an item without its skills or bullets fill in defaults from `backend/app/defaults.py`, the one place phase 5's AI suggestions plug in. In the front end, `docsApi(kind)` (`frontend/src/shared/api/documents.ts`) gives both one shape, and the same pages (`DocumentsPage`, `DocumentPage`) show either kind. `DocumentPage` lays out the tree as nested lists whose levels open and close: `Disclosure` for the top levels (`HeaderFields`, `DocumentTree`, and `LetterParts`), and `OrderedList` rows with `details` below them. Each row's View and Edit opens its item through the library's `useItemDialogs`, with a `Placement` (`itemHost.ts`): the row's button to return focus to, and how its New version takes the item's place here (the tree's `.../version` and `replaces` endpoints), which the view calls through `host.placed` instead of its library `versions` endpoint. Other changes in the dialog read the document again through `onReload`, which `DocumentPage` doesn't record for Undo. The tone, greeting, and sign-off save each change as it's made, and the header with its own "Save header" (each combination of its values being a saved header); `DocumentPage` runs those saves one at a time, each from the document the last one returned, so quick changes don't undo each other, and keeps the document as it was before each change for Undo and Redo (sending back the fields with the document's `PUT`, and the tree with `PUT .../tree`). `OrderedList` ids can be strings for a section's mixed items (`kind:item_id`). In the tree, each list's `OrderedList` uses `moreOptions`: the rest of what the library lists there, as checkboxes behind a "More options" level (`MoreOptions`), added together. `AddContent` adds anything else to a section type first, and `treeItems.ts` holds what the tree and it share (item names, the default type, each kind's new-item fields).
- **Job postings:** `backend/app/routers/job_postings.py` (`/api/job-postings`) creates, edits, and deletes postings and sets a posting's header (`PUT /api/job-postings/{id}/header`, finding or adding the header with exactly those values) and its tracking (`PUT /api/job-postings/{id}/tracking`: the dates and contacts). `backend/app/routers/interviews.py` (`/api/job-postings/{id}/interviews`) adds, changes, and deletes its interviews, with `also_posting_ids` for the other postings each covers. A posting's `GET` lists its resumes and cover letters (`versions`), a suggested header until it has one, its tracking and interviews, the organization's other postings (`same_organization`), and the interviews a delete would remove. Resumes and cover letters are started for a posting through their own `POST` and `.../copies` endpoints, with a `job_posting_id`; `posting_for_version` and `posting_header_id` in `documents.py` check the posting. In the front end, `postingsApi` (`frontend/src/postings/postings.ts`), `PostingsPage`, and `PostingPage`, which starts versions with `StartVersion` and tracks the application with `Tracking` and `Interviews`.
- **Front end:** each table has a typed API module (in `frontend/src/shared/api/`, or `frontend/src/library/` while only the library uses it) and a page in `frontend/src/library/`, with a route under `/library` in `frontend/src/App.tsx` and an entry in `LIBRARY_PAGES` (`frontend/src/library/libraryPages.ts`), which lists it in the library's sub-nav and landing page. A new mode goes in `frontend/src/modes.ts`. Pages keep the user's input on errors, highlight the failing field, and list what a delete affects before confirming, using the shared pieces in `frontend/src/shared/components/` (`ConfirmDelete`, `NameForm` for one field, `FieldsForm` for several, `OrderedList`) and the library's own (`UsedBy`, `BulletList`, `NameList`, `Collapsible`). Each item is a `LibraryCard` (`frontend/src/library/LibraryCard.tsx`): its title as a heading, a short summary, and View and Edit, which opens the item's dialog. Each page sorts its cards with `sortByName` (`frontend/src/shared/sortByName.ts`) and shows its `SORT_NOTE`. Hidden items go last, in `HiddenItems` (`frontend/src/library/HiddenItems.tsx`), each card with an `UnhideButton` that `useUnhide` saves. `ItemParts` offers Hide or Unhide (`onSetHidden`), and leaves out Delete when a sent application uses the item (`usedBySent`). Every picker, in the library and in a resume's or cover letter's tree, leaves hidden items out with `offered` (`frontend/src/shared/offered.ts`), and the backend's defaults leave them out too; `backend/app/hiding.py` has the shared `PUT .../hidden` helper and the check that refuses deleting what a sent version uses. Each page gets its dialog from `useItemDialogs` (`frontend/src/library/items/ItemDialogs.tsx`, on the shared modal `Dialog`), passing its `load` and its notice's setter. The dialog shows one item at a time through that kind's view in `frontend/src/library/items/` (`ExperienceItem`, `BulletItem`, and so on, picked by `ItemView`), which reads the lists it needs itself (`useItemData`), so any page can show any kind. A view lays out the same parts for every kind (`ItemParts`): the item's form, then New version and Delete (each named for its item, as `New version of "[item]"`, `Hide "[item]"`, and `Delete "[item]"`, from the view's `name`), which open their form or confirm in place of it, then each part (lists, "Used by") in a `Collapsible`, which shows a count and starts open unless it's empty. Names inside it (an `OrderedList` row with `onOpen`, a `NameList` with `refs`, a `BulletList`'s bullets) show their item in the same dialog through `useItemHost` (`itemHost.ts`), with "Back to [the item before]"; "Used by" names link to their resume, cover letter, or posting. Saving, adding a version, and deleting close the dialog, read the page's lists again, then say so on the page and move focus to the item's View and Edit button (`editId`) or the page heading. Fields and labels the views and pages share are in `itemFields.ts`. Tests find a card with `findCard`, open its dialog with `openItem`, and wait for one with `loadedDialog` (`frontend/src/test/openCard.ts`); `renderItem` (`frontend/src/test/renderItem.ts`) renders a view with a stand-in dialog. Tests stub the API with `frontend/src/test/stubApi.ts`, which answers each request from its replies in order and then keeps giving the last one, since a page and its dialog each read the lists.

## Accessibility
Every component and page is accessible and tested for it from the start, in three layers. Every test run (all files, one file, or a watch-mode rerun) runs the first two:
- **Whole-front-end checks** (`frontend/a11yChecks.ts`, Vitest global setup) stop the run before any test if a `.tsx` file has no sibling `.test.tsx`, if oxlint's jsx-a11y rules fail, if a text color in `index.css` is below 4.5:1 contrast (axe can't measure contrast in jsdom), or if a CSS module sets its own color instead of using a variable from `index.css`. The jsx-a11y rules (`frontend/.oxlintrc.json`) are all errors except `prefer-tag-over-role`, which is off because `role="status"` is announced more reliably than `<output>`.
- **axe-core in the tests** (`frontend/src/test/axe.ts`): `src/test/setup.ts` runs axe after every test that rendered something, so every front end test is an accessibility test. Tests call `expectNoA11yViolations()` themselves for states they pass through before the end, so every state gets checked: loading, loaded, empty, load error, form open, saving, validation error, delete confirm. `App.test.tsx` checks each route as a whole page (landmarks, one `h1`).
- **Review:** the `/a11y` skill covers what tools can't: focus, keyboard use, announcements, and names that make sense out of context. It reviews the whole front end each time, not just the change, since a change in one place often affects others. A Claude Code Stop hook asks for it whenever a turn changed front end files.

Patterns the pages follow:
- **Focus:** a form or delete confirm that opens in place takes focus: the first field, or Cancel. When it closes, focus goes back to the button that opened it (`useFocusLater` in `frontend/src/shared/hooks/`), or to the page heading after a delete. Moving to another page focuses that page's heading (the shell in `App.tsx` does this), so every page's `h2` has `id={PAGE_HEADING_ID}` and `tabIndex={-1}`.
- **Names:** buttons repeated on every card or row name their item (`aria-label='Delete "Freelance"'`), starting with the visible text: a card's or tree row's View and Edit, a dialog's New version, Hide, and Delete, each row's Move and Remove, and each list's Add (`Add to [list]`). In a resume's or cover letter's tree, where one item can be in more than one place, a row's View and Edit, Move, Remove, and the name that opens it also say where it is (`View and Edit React under Front End in Skills`, through `OrderedList`'s `where`). A list's picker has a visible "Choose one to add" label, with " to [list]" added for screen readers only (`visually-hidden`).
- **Dialogs:** an item's dialog is the shared `Dialog` (a native modal `<dialog>`, in `frontend/src/shared/components/Dialog/`), named by its heading. The heading takes focus when it opens and each time it shows another item. Tab and Shift+Tab wrap inside it, and when the focused control is removed (a list row, a form that closed) focus goes to the heading. Escape and Close close it from any depth, unless a control inside used Escape itself (`OrderedList`'s move calls `preventDefault`). When it closes, focus goes back to what opened it, to the saved item's View and Edit (`editId`) on a library page, to the row's View and Edit in a tree, or to the page heading after a delete. One dialog shows at a time, never one inside another.
- **Messages:** errors use `role="alert"` and are linked to their field with `aria-describedby`. The page's `role="status"` notice is always rendered, so screen readers announce changes to it. A `Dialog` has its own (`notice`), since the page's can't be reached behind it: a change that keeps the dialog open (a tone's rule deleted) is said there, and one that closes it (Save, Delete) is said on the page once the dialog is gone.
- **Disabled buttons:** a button that may have focus when it stops being available (Save while saving, Add with nothing picked) uses `aria-disabled` and ignores clicks, so focus isn't lost.
- **Reordering:** lists are reordered with `OrderedList`'s grip handle: drag it, or (keyboard) Space or Enter to pick up, ↑/↓ to move, Space or Enter to drop, Escape to put it back. A click without dragging picks the item up too, and the other rows offer "Move here", so no step needs dragging (WCAG 2.5.7). Each step is announced in the list's live region.
- **Pages:** each sets its tab title with `usePageTitle`. The shell has `header`, `nav`, and `main` landmarks; a mode with its own pages (the library) adds a second `nav`, named for the mode. A mode's main nav link is marked `aria-current="true"` on its sub-pages and `"page"` on its own landing page.

## AI integration
- **Direct API calls, not an agent.** The user flow is a fixed sequence, so the backend runs each step and makes one Claude request per step: extract the posting, suggest sections, suggest each section's content, suggest rewordings, review the whole thing.
- **Model:** Claude Opus 5.5 (`claude-opus-5-5`), with effort set per step: lower for extracting a job posting, higher for rewording and the final review.
- **Structured responses:** each request defines the shape of the reply with a Pydantic model, so the app gets data it can use directly. For example, a skills suggestion comes back as an ordered list of `skill_id`s, each with a reason, ready to show for approval.
- **Streaming** for longer outputs (rewritten sections, the final review), so text appears as it's written.
- **Prompt caching:** the parts that stay the same across a session go first in every request and are cached: writing rules, library content, then the job posting. The step-specific request comes last.
- **Job posting extraction:** Python fetches the HTML, and Claude pulls out the job description, organization, role title, and values as structured data. If fetching fails, the user pastes the text in instead. Error handling for these and every other failure is in [API_ERRORS.md](API_ERRORS.md).
- **Writing rules:** a code check finds banned words, and Claude judges only the flagged ones (technical term or filler?), per [WRITING_RULES.md](WRITING_RULES.md).

### API key and cost
- API usage is billed separately from a Claude.ai subscription, through an Anthropic Console account.
- The key lives in a `.env` file read only by the backend (`ANTHROPIC_API_KEY`), and `.env` is in `.gitignore`. The React front end never sees the key; all Claude calls go through FastAPI.
- Rough estimate: well under $1 per application with caching. Measure real usage once the app runs.
