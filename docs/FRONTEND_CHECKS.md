# Front End Checks

Rules the database does not enforce, so the app must handle them. See the database schema in [DATABASE.md](DATABASE.md). When a rule fails, the backend returns the error code named here (see [API_ERRORS.md](API_ERRORS.md)), and the request changes nothing.

## Delete warnings
The five built-in sections ("Summary", "Skills", "Experience", "Projects", "Education") and the built-in "Other" skill category can't be deleted or renamed. The backend refuses with `BUILT_IN_PROTECTED`, and a database trigger blocks it as a backstop.

Most foreign keys use `ON DELETE CASCADE`, so deleting a row also deletes every row that refers to it. The exceptions (`header_id`, `sign_off_id`, `tone_set_id`, and `based_on_resume_id` / `based_on_letter_id`) are set to empty instead, as described below. Before any delete, warn the user and list what else will be removed or changed, including any sent versions it affects. Where a page can delete more than one kind of thing, its Delete buttons and warning name the kind: a posting's page says "Delete job posting" ("Delete job posting for Educator at Marigold?"), and a posting's resume or cover letter names its posting ("Delete resume for Educator at Marigold?"), since both are named for the posting. After a resume or cover letter is deleted, the app goes back to the page it was opened from: its posting's page when opened or started there, otherwise the list of resumes (or cover letters).

Cascades that remove more than the user might expect:
- **Section**: built-in sections can never be deleted, so don't offer the option. Deleting a user-created section removes it, and everything placed in it, from every resume and cover letter. The library items it listed are kept; they're just no longer listed under that section.
- **Skill category**: its skills stay in the library. Any skill no other category lists is listed under the built-in "Other" category. Resumes and cover letters keep showing the same skills, under "Other" (see "Deleting a skill category" below). The built-in "Other" category can never be deleted or renamed, so don't offer the option.
- **Skill**: removed from every category (`skill_category_skill`), project (`project_skill`), resume (`resume_skill`, `resume_project_skill`), and cover letter (`cover_letter_skill`, `cover_letter_project_skill`).
- **Experience / project**: removes it, and the bullets (and a project's skills) under it, from every resume and cover letter. The bullets and skills stay in the library and under any other role or project that lists them.
- **Bullet point / narrative content**: removed from every list (`experience_bullet_point`, `section_narrative_content`, etc.) and from every resume and cover letter that uses it.
- **Resume / cover letter**: removes only its own selections and its chat with Claude. Library items are kept. Versions copied from it stay; their `based_on_resume_id` / `based_on_letter_id` is set to empty.
- **Header**: job postings, resumes, and cover letters that use it are kept; their `header_id` is set to empty, so they show no header until the user picks another. List them in the warning.
- **Job posting**: deletes every resume and cover letter made for it, along with their selections. Its interviews that no other posting is linked to are deleted too (the app does this in the same transaction); interviews shared with another posting stay. List both in the warning.
- **Interview**: removed from every posting it was linked to. List the other postings in the warning.
- **Sign-off**: cover letters that used it are kept; their `sign_off_id` is set to empty, so they have no closing until the user picks another.
- **Tone** (`tone_set`): deletes its tone rules. Resumes and cover letters that used it are kept; their `tone_set_id` is set to empty.
- **Account**: deletes everything the account owns.

### Deleting a skill category
Deleting the category would remove its skill list and its resume and cover letter selections. Before deleting it, in one transaction:
1. List every skill in the category that no other category lists under "Other" (`skill_category_skill`), after the skills already there, keeping their order.
2. Find every `resume_skill_category` and `cover_letter_skill_category` row that uses it.
3. In the same resume or cover letter section, find the "Other" category row, or create one at the deleted category's `position`.
4. Move the selected skills (`resume_skill` / `cover_letter_skill` rows) under that "Other" row, after any skills already there, keeping their order. Skip skills already selected under "Other".
5. Then delete the category.

If any step fails, the transaction rolls back: the category, its skills, and every resume and cover letter stay exactly as they were. Return `INTERNAL_ERROR`, whose message says nothing was changed ("Something went wrong. Nothing was changed.").

## Accounts
- **New accounts get the defaults:** when the backend creates an account, add the starting writing rules and the "Sincerely" sign-off (the same rows `db/seed_defaults.sql` adds).
- **Scope every query to the current account.** Until logins exist, the app always uses the single owner account.
- **No cross-account links:** a resume or cover letter may only use library items and job postings from its own account. The database doesn't check this. Return `CROSS_ACCOUNT_LINK` if attempted.

## Versions
- **Base resumes / cover letters** (no `job_posting_id`) can be edited directly whenever the user wants. They're ongoing starting points.
- **Editing in place:** a base version, and a version for a posting until it's sent, is edited in place right away, with no step to start editing. Above its Copy and Delete buttons, its page says that edits save instantly, that Undo and Redo work only while the user stays on the page, that Copy (a new base version, `based_on_resume_id` / `based_on_letter_id` set to the original) keeps this version as it is, and that versions already sent don't change. Its name is changed under Contents with "New title", in a modal (a sent version's too, since its name is all that can change).
- **Never edit a tailored version to fit a different posting.** Starting from any earlier resume or cover letter, base or tailored, creates a new row with `based_on_resume_id` / `based_on_letter_id` set to the original.
- **Saving a tailored version as a new base:** the user can copy a tailored version into a new base resume (no posting) to reuse later.
- **Starting a new base version:** the New base form starts it fresh (with the defaults), as a copy of any existing resume or cover letter of the same kind, base or tailored, or from the user's own file or pasted text (see "Reading an existing resume or cover letter"), named by the user. A copy needs one chosen to copy (`VALIDATION_FAILED`, checked on the page). A copy follows "A copy" in "Starting a version for a posting", without the posting: `based_on_resume_id` / `based_on_letter_id` is set to the original, which never changes.
- **Resumes and cover letters connect only through their job posting:** there's no direct link between them. A resume or cover letter made for a posting gets that posting's `job_posting_id`, not the one of the version it was copied from.
- **Names of resumes and cover letters** are unique among the account's resumes (or its cover letters), ignoring capitals, so each is told apart in lists. A name typed when creating, copying, or renaming must be new (`DUPLICATE`, naming the one that has it). A copy starts as "Copy of [name]", or "Copy 2 of [name]" and so on when that's taken. A version for a posting, which the app names "[role title] at [organization]", gets " (2)", " (3)", and so on when another posting has the same role and organization, instead of being refused. A resume and a cover letter can share a name.
- **A base version's name is shown with "Base Resume" (or "Base Cover Letter") after it** everywhere but its own name field: in its title, the lists, "Start from", "Used by", and notices. The name itself is only what sets it apart ("Mentoring" shows as "Mentoring Base Resume"). The fields for a base version's name (new, copy, and New title) show the suffix beside them. The backend names them the same way in the lists of uses it returns (`shown_name` in `backend/app/versions.py`).
- **Telling versions apart:** where two library items in one list would read the same (two versions of a role with the same title, of a project, or of an education entry, two headers with the same name and headline, or two tones with the same name), each adds when it was added ("…, added Oct 31, 2026, 2:05:13 PM"). This covers the library cards and their buttons, the Sections page's lists, and a resume's or cover letter's More options and Add content.
- **Copy the whole tree.** A copy duplicates every join row under the original (sections, then items, then sub-items like skills and bullets), with new ids and the same `position` values. The library items themselves are not copied.

## Undo
- **Every change on a resume's or cover letter's page can be undone**, one step at a time back to when the page was opened, and redone until a new change is made. The history lasts only while the page is open. A sent version has nothing to undo.
- **What it puts back:** the document's fields (name, header, tone, greeting, sign-off, and signature name) and its whole tree exactly as it was (`PUT .../tree`), including the skills and bullets chosen under each item, even ones the library no longer lists under it.
- **Claude's draft too:** while a document has a draft, each change to it is a step, and undoing sends the draft back as it was. Approving the first draft saves to the library, so it can't be undone, and the history starts again.
- **The library isn't changed:** anything written to the library since (a new bullet, section, sign-off, or header, or a new row saved by an edit) stays there; undoing only takes it out of this document.
- **Ids are still checked:** an item deleted from the library since returns `NOT_FOUND` (the built-in "Other" category can be put back, since a document can show it), another account's returns `CROSS_ACCOUNT_LINK`, and a bullet twice in one section returns `DUPLICATE`. The step stays, to try again. A sent version returns `VERSION_LOCKED`.

## Sent versions are locked
Recording the date a posting was applied to (`job_posting.applied_on`) marks its resumes and cover letters as sent. From then on they're a record of what went out, so:
- **No edits:** their fields, sections, and selections can't be changed. Show them read-only and offer "Copy" instead: a new base version, or a version for another posting. The backend returns `VERSION_LOCKED` if a change is sent anyway.
- **Library edits don't reach them:** a resume or cover letter stores only which library items it picked (their ids, in its join tables), and prints each item's text and fields (a project's title, `done_for`, and dates, for example) from the library row. So editing a library item that a locked version uses (any kind: a header, section title, sentence, skill category, skill, role, project, bullet, education entry, sign-off, or tone) saves the change as a new row instead of changing the original. The new row is listed under the same parents and lists the same children as the original. Locked ones keep the original, and only the ones in progress the user checks switch to the new row (see "Changing an item" below).
- **A sent version can't be deleted** (`VERSION_LOCKED`: "This resume was sent, so it can't be deleted. Hide it instead."), so the record of what went out is kept. Its page offers Hide (or Unhide) in place of Delete. Deleting its posting still deletes it, after the posting's warning. A library item a locked version uses can't be deleted (`VERSION_LOCKED`); it can be hidden instead (see "Hiding").
- **Unlocking:** clearing `applied_on` unlocks the posting's versions. Warn the user first, in the tracking form, before anything saves. Changing the date to another date doesn't warn, since nothing unlocks.
- **Renaming** a locked version (`name`) is allowed, since the name is only a label. Changing any of its other fields (header, tone, a letter's greeting, sign-off, or signature name) returns `VERSION_LOCKED`.

## Changing an item
Every kind of library item changes the same way: edit it in its dialog, then check which resumes and cover letters in progress get the change. A resume or cover letter prints its items from their rows (a role's `role_title`, `organization`, `location`, and `dates`, a bullet's text, a section's title, a header's values), and a user may want different versions in different resumes in progress (with dates or without, or a bullet worded for one job, for example). Tones aren't printed, but they follow the same rule, so a sent version keeps the tone it was written with. This covers headers, sections, narrative content, skill categories, skills, roles, projects, bullets, education, sign-offs, and tones. So editing one:
- **Sent versions never change.** If a locked version uses it, the change is saved as a new row (see "Sent versions are locked").
- **Ask which resumes and cover letters in progress get it.** If unlocked ones use it, list each with a checkbox, none checked to start (`apply_to`, a list of `{kind, id}`). Only unlocked ones that use it can be picked (`VALIDATION_FAILED`, field `apply_to`).
  - **Every one checked:** the change is made in place, unless a locked version uses the row; then it's a new row and they all switch to it.
  - **Some or none checked:** the change is saved as a new row. The checked ones switch to it, and the rest keep the original until the user picks the new one.
  - **Edited from a resume's or cover letter's tree** (its row's View and Edit): that one gets the change without asking, and the checkboxes list only the others in progress.
- **Nothing uses it:** edit it in place.
- **A note above the fields says what Save will do,** whenever the item is opened from a resume or cover letter, or something in progress uses it: "Saving changes it in this resume, and in the others you check below."; with no others in progress, whether Save adds a new version to the library ("Saving adds a new version to your library, used in this resume only. Other resumes keep the original.", when anything else uses it, sent or not) or changes the item itself ("Saving changes it in your library and in this resume."); or, from the library, "Saving changes it only in the ones you check below; the rest keep it as it is." It follows the note for a sent version or a built-in one, when there is one; that note already says a new one is added, so then it only says "The new one goes in your library, used in this resume only." After saving, the notice names the new row when one was saved, and says who uses it.
- **Nothing changed saves nothing:** values the same as the original return it unchanged (status 200).
- **A new row** is listed right after the original wherever the original is listed, and lists the same children: a section under no parent, with the same lists; a category in its sections, with the same skills; a skill in every category and project; a role or project in its sections, with the same bullets (and a project's skills); a bullet under every role, project, and section; an excerpt or education entry in its sections; a tone with copies of its rules. A new row starts unhidden. An excerpt's edit can also change which sections list it: that never makes a new row on its own, and when the text does, the sections chosen apply to the new row and the original keeps its own.
- **No "New version":** there's one way to change an item. To keep two wordings side by side, write the second as new content.

Edge cases:
- **Built-in sections and "Other"** are never renamed, so a new title for one always saves a new section or category, listing only the account's own items, and the checked ones switch to it.
- **Names stay unique:** a new section title, category name, skill name, or tone name must be new in the account (`DUPLICATE`), whether the edit is made in place or saved as a new row. A tone saved as a new row can keep its original's name, and the two are told apart by when each was added (see "Telling versions apart").
- **Headers** list postings, not their resumes and cover letters, since a posting's versions all share its header: the checkboxes name the postings in progress (`{kind: "job_posting", id}`) and the base resumes and cover letters that use it (the header's `in_progress`). A new header reuses an identical one if there is one. See "Headers".
- **Tones are saved whole:** the name and every rule, in order, with one Save (see "Writing rules").

## Headers
- **A posting's header** is the user's header for their application. Right after a job posting is created, the user picks it (`job_posting.header_id`). Suggest the most recently used header, with the headline based on the posting's job title: the title only, never the organization ("Full Stack Engineer", not "Full Stack Engineer at Cascadience"), so a trailing organization name (after "at", "@", or a dash, bar, comma, or colon) is trimmed off the posting's role title (`job_title` in `backend/app/routers/job_postings.py`). Nothing is saved until the user uses the suggestion, changed or not. After that, "Save header" points the posting and all its resumes and cover letters at the header with exactly those values, or a new one. Once the posting is applied to, its header is locked with its versions (`VERSION_LOCKED`).
- **A posting's resumes and cover letters** use the posting's header, and nothing else: the header is picked and changed only on the posting, and a version's page shows it read-only as the "Application header", with a link to the posting. Picking another header for a version, when starting it or later, returns `VALIDATION_FAILED` (`header_id`). A posting with no header yet asks for one first (see "Starting a version for a posting").
- **New base resumes and cover letters** start with the header of the version they're copied from, or the most recently used header when starting fresh.
- **Changing the headline or contact details** in the header's dialog follows "Changing an item": sent versions and applied postings keep the header they went out with, and only the postings and base resumes and cover letters in progress that the user checks get the change. Applications in progress at the same time may need different headers, so none is checked to start. Whenever a header would be added (the New header button, or an edit saved as a new header), reuse an existing header with the exact same values instead of adding a duplicate.
- **Picking header values on a base resume or cover letter, or a posting:** each value is picked on its own (from the values saved in any header, or typed in new in a small modal, which starts with the current value and whose Apply only puts it in the form). Nothing saves until "Save header", so trying combinations out never adds headers. Saving never changes a saved header: the document (or the posting and its versions) points at the header with exactly those values, or a new one is added. A sent version, or an applied posting, returns `VERSION_LOCKED`.

## Starting a version for a posting
- **Where:** on the posting's page. A new resume or cover letter for a posting starts one of five ways: tailored by Claude (the default; see "Claude's suggestions"), as a copy of any earlier one as is, base or tailored, from scratch, with no sections (`empty`), or from the user's own file or pasted text (see "Reading an existing resume or cover letter"). Every way but a copy takes a tone (none to start); a copy keeps the original's. A copy needs one chosen to copy (`VALIDATION_FAILED`, checked on the page). It gets the posting's `job_posting_id` and the posting's header.
- **One of each per posting:** a posting has at most one resume and one cover letter, edited in place until the posting is applied to. Once it has one, its page links to it and offers no Start for that kind; starting a second returns `DUPLICATE` (`job_posting_id`), naming the one that exists. Trying a different approach means changing that one (or making a base copy of it).
- **The posting must have a header first.** Without one, the backend returns `VALIDATION_FAILED` (`header_id`), and the page doesn't offer to start one.
- **Not after applying:** a posting with an `applied_on` date gets no new versions, since its versions are a record of what was sent. The backend returns `VERSION_LOCKED` (`job_posting_id`), and the page doesn't offer to start one. Start a base version instead.
- **A copy** keeps the original's tone, sections, and selections, with `based_on_resume_id` / `based_on_letter_id` set to the original, which never changes. A cover letter copied for a posting greets that posting's organization ("[organization] Hiring Team"), whatever the original's greeting was, and keeps its sign-off and signature name.
- **Name:** nobody types one. A version is named "[role title] at [organization]", which always fits (`name` allows 204 characters, the longest role title and organization with " at "), and the posting's page links to it as "Resume" or "Cover letter". The name is set once, so editing the posting later doesn't change it. Rename still works from the version's page.
- Another account's posting returns `NOT_FOUND`.

## Tracking an application
- **Dates and contacts** can change at any time, including after the posting is applied to. A date that can't be read returns `VALIDATION_FAILED`. Clearing the applied date warns first (see "Sent versions are locked").
- **An interview needs a date** (`VALIDATION_FAILED`, `interview_on`). It can be added or changed at any time, including after applying.
- **An interview always has a posting:** it's reached through a posting it's linked to and stays linked to that one. Through a posting it isn't linked to, it returns `NOT_FOUND`.
- **Other postings an interview covers** are the organization's, matched ignoring capitals, and are offered as checkboxes. The backend only checks they're the account's own: `also_posting_ids` returns `NOT_FOUND` for a missing posting, `CROSS_ACCOUNT_LINK` for another account's, and `DUPLICATE` for a repeat or the posting it's reached through.

## Hiding
- **Any library item can be hidden** (`PUT /api/<items>/{id}/hidden` with `{"hidden": true}`, or `false` to unhide), used or not, to set it aside without losing it: headers, sections, narrative content, skill categories, skills, roles, projects, bullets, education, sign-offs, and tones. The built-in sections and "Other" can't be hidden, since every account shares them (`BUILT_IN_PROTECTED`).
- **Not offered anywhere new:** a hidden item is left out of every list that offers items to add or pick (a library dialog's Add pickers, a page's "List it under" sections, a resume's or cover letter's More options and Add content, and the header, tone, and sign-off choices), and out of the defaults (`backend/app/defaults.py`). A choice that's already made still shows it.
- **Kept where it's used:** every resume and cover letter that shows it keeps it, sent or not, and every parent that lists it keeps listing it. Hiding changes nothing in them, so it never saves a new row, even when a sent version uses it.
- **On the library pages:** each page ends with "Hidden (n)", closed to start, listing its hidden items with Unhide and View and Edit. Hidden items aren't in the page's other groups. The item's dialog says it's hidden and offers Unhide in place of Hide.
- **Can't delete what a sent version uses:** deleting a library item that a locked resume or cover letter uses returns `VERSION_LOCKED` ("A sent application uses this …, so it can't be deleted. Hide it instead."). Its dialog offers Hide in place of Delete, with that note. A sent resume or cover letter itself can't be deleted either, only hidden (see "Sent versions are locked"); deleting its posting still works after its warning.
- **Resumes and cover letters can be hidden too** (`PUT /api/resumes/{id}/hidden`, `PUT /api/cover-letters/{id}/hidden`), sent or not; a sent one's page offers Hide, since it can't be deleted. A hidden one is left out of "Start from" when starting a new base version or a posting's version, and its list page shows it last under "Hidden (n)", closed to start, with Unhide. Nothing it shows changes.
- **Editing:** a hidden item can still be edited. A new row saved by an edit starts unhidden.

## Item dialogs
Every library item is changed in one place, its dialog, wherever it's shown: a library card's View and Edit, a name inside another item's dialog, or a row of a resume's or cover letter's tree.
- **What it holds:** the item's form (Save), with the note saying what Save will do and the checkboxes for the ones in progress (see "Changing an item"), then Hide (or Unhide) and Delete, then its own lists, the parents that list it, and "Used by". Delete opens its confirm in place of the form; nothing is deleted until its button is pressed, and going back deletes nothing.
- **What closes it:** Save and deleting close it, then the page reads its lists again and says what happened. Changing one of its lists (adding, removing, reordering) and hiding save right away and keep it open. Cancel and Close save nothing.
- **One at a time:** a name inside it shows that item in the same dialog, with "Back to [the item before]"; it never opens a second dialog. Only the item first opened knows the resume or cover letter it was opened from (see "From a resume's or cover letter's tree" below); one shown from a name inside it is a library item, edited as from the library.
- **Same rules as anywhere else:** an edit to an item a sent version uses saves a new row ("Sent versions are locked"), every edit asks which resumes and cover letters in progress get it ("Changing an item"), a delete lists what it affects ("Delete warnings"), and an item a sent version uses offers Hide instead of Delete ("Hiding").
- **From a resume's or cover letter's tree:** every row (a section, a role, project, or education entry, a skill category or skill, a bullet, and narrative content) has View and Edit, which opens its item's dialog, the same one the library shows. Saving there changes the item for this document without asking, and for the others in progress the user checks (see "Changing an item"); when that saves a new row, this document switches to it, keeping what's under it (a role's bullets, a category's skills, a section's items). Saving, hiding, or deleting changes the library item, and the document is read again to show the result; these aren't changes to undo in the document. A read-only document has no View and Edit.

## Suggesting and adding items
- **Defaults** (`backend/app/defaults.py`; a posting's document started with Claude starts from Claude's draft instead, and the defaults still fill what's added afterward, by hand or from the chat): each level of a resume's or cover letter's tree starts with what the most recently updated other document of the same kind showed for the same parent, in its order. A new document gets the sections of the latest one that has any; an added section gets the items of the latest one that put anything in it; an added role, project, or category gets the bullets and skills it showed in the latest one that showed any. When no other document has, the default is the first 3 the library lists under the parent (for a section, of the kind it lists most), and no sections for a new document. Skills and bullets the parent no longer lists are left out, and so are bullets already in the section. A placed item's skills or bullets sent explicitly (even an empty list) are used instead. A new document created with `empty` ("Build from scratch") gets no sections at all. Everything else the library lists there is offered under "More options".
- **No content restrictions:** any kind of library item can go in any section, including mixes in one section, and any section can go in any resume or cover letter.
- **New items are listed under their parent:** a new item is added to the list of the section, category, role, or project it's created in (e.g. a new bullet written under a role goes in that role's `experience_bullet_point` list). A new skill written under a project on a resume or cover letter is listed under the project and the built-in "Other" category, since every skill has a category. A new skill's name must be new (`DUPLICATE`), and so must a new section's title, written from "New section title" (it's added last, empty, since nothing is listed under it yet). New skill categories, experience, projects, and education entries default to the built-in "Skills", "Experience", "Projects", and "Education" sections, and new skills to the built-in "Other" category. The user can choose any other section or category (or, for a skill category, no section). Narrative content can be written on the Narrative content page too, where the user checks any number of sections to list it under (or none); the edit form changes that choice the same way. When a text edit saves a new excerpt (see "Changing an item"), the sections chosen apply to the new one and the original keeps its own.
- **Unlisted items:** an item no parent lists (e.g. after its role was deleted) stays in the library. Show it in the library so the user can list it again or delete it.
- **Library order:** each library page lists its cards A to Z by the name each card shows (`sortByName` in `frontend/src/shared/sortByName.ts`: capitals and accents ignored, numbers in number order), within each of its groups, and says "Sorted A to Z." under its heading. Items with the same name keep the order they were added, so versions stay together. Every choice the user picks from is sorted the same way: dropdowns and checkbox lists (pickers, More options, Add content's item, the tone and sign-off, "List it under", "Start from", which resumes and cover letters get a change), A to Z within each of their groups, with fixed choices kept first: "None" (or "Choose a …"), then "New …", before every saved item, so screen reader and keyboard users reach it without going through them all. Other fixed choices ("No section") may come last. The one exception is Add content's "Type of content", which follows a resume's usual order. A parent's lists (a section's items, a role's bullets, a category's skills) keep the order the user gave them, since it's the default order in resumes and cover letters.
- **A section's dialog shows the kinds it holds:** its default kind (by id for the built-in sections: narrative content for Summary, skill categories for Skills, roles for Experience, projects for Projects, education for Education), and every kind it already lists. The other kinds are under "More options", closed to start, or open for a section that lists nothing. What shows is decided when the dialog opens, so a kind added to from More options stays there until the next time.
- **Skills always have a category:** taking a skill out of the only category that lists it lists it under "Other" instead. Taking a skill out of "Other" when no other category lists it returns `VALIDATION_FAILED`; add it to another category first.
- **"Other" isn't listed under sections:** listing it under a section returns `VALIDATION_FAILED`.
- **Mixed sections:** items placed directly in the same resume or cover letter section share one `position` numbering across all join tables. Assign and reorder positions across item types together, so a sentence, an experience, and a bullet in one section have a single order.
- **Section contents**: when suggesting content for a section, start with the items the section lists (`section_narrative_content`, `section_skill_category`, `section_experience`, `section_project`, `section_bullet_point`, `section_education`), but let the user add any library item to any section. When adding content by hand, the type of content starts as narrative content in a cover letter, and in a resume as the kind the section lists most (none when it lists nothing). Never decide from the section's `title`.
- **Duplicates:** a section title, skill category name, skill name, or tone name already used in the account (ignoring capitals, and counting the built-in sections and "Other"), or the same item picked twice under one parent, returns `DUPLICATE`. The message names the existing item so the user can use it instead.
- **Section titles in output**: print section titles in a resume. Never print them in a cover letter, where they're descriptors for the user only. The Sections page groups sections the same way: resume headings (built-in or used by a resume), cover letter labels (used only by cover letters), and ones not used yet.
- **Skills in a category**: suggest skills the category lists in `skill_category_skill`, in its default `position` order. Any skill in the library can be picked, since skill sets overlap: the category's own come first, and the rest under "Other skills in your library", where adding one also lists it last under the category in `skill_category_skill`, in the same request, so later documents and Claude offer it there.
- **Skills in a project**: suggest skills from `project_skill` for that project, in its default `position` order. The user picks which ones appear on each resume or cover letter (`resume_project_skill`, `cover_letter_project_skill`). Any skill in the library can be picked: the project's own come first, and the rest under "Other skills in your library", where adding one also lists it last under the project in `project_skill`, in the same request, so later documents and Claude offer it there.
- **Bullets**: only offer bullets the selected experience or project lists (`experience_bullet_point` / `project_bullet_point`). Suggest a subset that fits the posting, leaving out bullets too similar to ones already chosen. A bullet's `resume_experience_id` / `resume_project_id` (or the cover letter equivalents) must belong to the same section as the bullet. Leave both empty for a bullet listed directly in the section. A bullet that breaks these rules returns `VALIDATION_FAILED`. A bullet can be placed once per section (directly, or under one role or project); placing it again returns `DUPLICATE`.
- **Default sign-off:** new cover letters use the account's "Sincerely" sign-off. The user can pick another or write a new one in place ("New sign-off"), which is saved to the library and used by the letter; one with the same text (ignoring capitals) is reused instead. A sent letter returns `VERSION_LOCKED`.
- **Name under the sign-off:** the field starts as the header's name. Typing the header's name, or clearing the field, stores it empty (`signature_name` null), so it follows the header; anything else is saved as typed.
- **Default greeting:** when creating a cover letter, or copying one for a posting, set `addressee` to "[organization] Hiring Team" from the job posting (or "Hiring Team" with no posting). Keep any value the user types in instead. A letter Claude tailors keeps the default until its draft is approved with Claude's greeting (see "Claude's suggestions").

## Claude's suggestions
- **A draft first:** Claude's suggestion for a posting's resume or cover letter waits in the document's `draft` until the user's first review. Nothing in it is saved to the document or the library until "Approve first draft", which writes what the user kept and clears it. The first pass only accepts or rejects Claude's suggestions, so what the user throws out never reaches the library: each section, item, bullet, and skill has a badge saying where it came from ("Original": in the document Claude started from, or the document's own tree when it was read from the user's file; "Library": brought in by Claude; "Claude": Claude's wording or new text), and a "Rationale" level with Claude's reason (why it's kept, brought in, or reworded) and, for a rewording, the other wording with "Use the original" or "Use Claude's wording". What's marked "Library" or is Claude's new text can be rejected, which takes it out of the draft; nothing is reordered or added here, and the rest is done after approving.
- **A cover letter's extras:** Claude writes new paragraphs from the posting where the letter needs one the library doesn't have (why this organization, how the person meets its main requirements), one sentence per narrative content item, backed by the library. A new paragraph goes in a library section that plays the same role, or in a new section Claude titles, marked "Claude" with Reject. A new title that matches a visible library section's, ignoring capitals and spacing, is that section; a second new section with the same title, one over 100 characters, or one with no title is left out and logged. A resume gets no new sections. Claude also suggests the greeting: the name the posting or its `contacts` gives for who is hiring, exactly as written (a title such as Ms. only if it's written with one). With none, one over 100 characters, or the letter's own greeting, there's nothing to review and the letter keeps "[organization] Hiring Team". While the draft has Claude's greeting, it takes the place of the Greeting field, marked "Claude", with its reason and "Use the usual greeting" (and back, "Use Claude's greeting").
- **Started with the document:** `POST /api/resumes/tailored` (or `/api/cover-letters/tailored`) creates the posting's document empty and stores Claude's suggestion as its draft, in one transaction, so if Claude fails (`AI_UNAVAILABLE`) nothing is created and the user can try again. With `start_from_id` (the Start form's "Start from", which offers the same saved ones as a copy), Claude starts from that one instead of picking, and the draft names it as the starting point whatever Claude says. One that isn't the account's own or has no sections returns `VALIDATION_FAILED` (`start_from_id`) before Claude is asked. Claude's reply is the whole document; one with fewer than half the starting point's items means Claude listed only what it changed, so it's asked once more, and that answer is the draft.
- **Only for a posting's document in progress:** a base version can't be tailored (`VALIDATION_FAILED`, `job_posting_id`), nor one for a posting that was applied to (`VERSION_LOCKED`), and a posting that already has one gets no second (`DUPLICATE`), so there's one draft at a time. There's no "Suggest again"; the chat at every level works on the document instead.
- **Reviewing changes only the draft:** each change in the first pass sends the draft's whole tree (`PUT .../draft`), checked as Claude's reply is, but refused instead of left out (`VALIDATION_FAILED`, `sections`): an id that isn't the account's own or is hidden, a bullet its item doesn't list, a bullet twice in a section, Claude's text anywhere but where Claude put it, more than once, or (for new text) gone back to an original it doesn't have, or one of Claude's new sections that isn't in the draft or is there twice. With it goes whether a letter keeps its usual greeting (`use_default_greeting`). Claude's texts and titles themselves never change. Undo and Redo send the draft back the same way.
- **Finishing:** `POST .../draft/finish` saves each of Claude's texts the draft uses (not gone back to the original) as a new library row, listed as in "Rewordings", or for new text under the section, role, or project Claude put it in, and places the tree with them, in this document only. Claude's new sections the draft still has are added to the library first, or the saved section with the same title (ignoring capitals, hidden ones too) is used, and their new text is listed under them; new text kept for later from a new section that was rejected stands alone, listed under no section. A letter gets Claude's greeting unless the user kept the usual one. `keep` lists Claude's texts the draft doesn't use that the user keeps for later, saved the same way but not placed; any other key returns `VALIDATION_FAILED` (`keep`). The document's `based_on_resume_id` / `based_on_letter_id` is set to the one Claude started from, if it still exists, and the draft is cleared. With no draft, both endpoints return `VALIDATION_FAILED`.
- **No sent drafts:** recording a posting's applied date while one of its documents has a draft returns `VALIDATION_FAILED` (`applied_on`): approve the first draft first.
- **Only the account's own items, where they can go:** every id Claude names must be the account's own and not hidden, and a bullet under an item must be listed under it in the library (see "Suggesting and adding items"), while any of the account's visible skills can go under a skill category or project, as on the page; approving the draft lists each kept skill under its category or project in the library, if it isn't already. Anything else is left out of the draft and logged, so one mistake doesn't lose the whole suggestion.
- **A copy doesn't copy the draft.**

## Chat with Claude
- **One conversation per document:** each resume and cover letter keeps its whole chat (`chat_message`), in order, read by `GET /api/resumes/{id}/chat` (or `/api/cover-letters/{id}/chat`) for any of the account's own, sent ones too. Another account's returns `NOT_FOUND`. A copy doesn't copy it.
- **Sending a message:** `POST .../chat` with `text` (1 to 4,000 characters after trimming, or `VALIDATION_FAILED`, `text`) and `about`: the whole document, a section in it, or an item in it (an entry in a section, or a bullet or skill under one), with any unsaved values from the item's dialog. A section or item the document doesn't have returns `VALIDATION_FAILED` (`about`). A sent document returns `VERSION_LOCKED`, and one with a draft from Claude `VALIDATION_FAILED` (approve the first draft first). These are checked before Claude is asked.
- **The reply streams, then saves:** the response is a stream of JSON lines: Claude's text as it's written, then either the saved user and Claude turns, or an error in the shape in [API_ERRORS.md](API_ERRORS.md) (`AI_UNAVAILABLE` when Claude fails). Both turns are saved in one transaction only once the whole reply is in, so a failed reply saves nothing, and the panel keeps what the user typed, with Retry.
- **Claude's proposals are checked like its suggestions:** each proposed change must name what the document has (to reword, remove, or move) or a visible item of the account's own (to add), a bullet under a role or project must be listed under it in the library, while any of the account's visible skills can go under a skill category or project (as on the page), only narrative content and bullets are reworded, and new text is only for narrative content, bullets, and a new skill under a skill category or project (up to 100 characters, and not a name a visible skill already has, ignoring capitals; Claude is told to add that one instead). Claude is told it can propose anything the page can do, and never to send the user to the library first. Anything else isn't shown, and the next turn tells Claude it was left out and why. Nothing is changed until the user applies a proposal.
- **Applying a proposal** (`POST .../chat/{message_id}/proposals/{id}/apply`) makes an ordinary change to the tree in one transaction, kept for Undo on the page: it's checked again against the document and the library as they are now (`VALIDATION_FAILED` when it no longer fits, and nothing changes), an added section or item gets the defaults it would get added by hand, and Claude's new or reworded text becomes a new library row used in this document only (a rewording listed right after its original, as in "Rewordings"; new text under the section, role, or project it goes in). A skill added under a skill category or project is listed under it in the library too, and a new skill is saved as the page saves one: listed under its category, or under "Other" and the project, with a name new to the account (`DUPLICATE`, hidden skills too). Only a pending proposal can be applied (`VALIDATION_FAILED`). Undo takes back the change but leaves the card "applied"; Claude sees the document as it is in the next message.
- **Dismissing** (`PUT .../chat/{message_id}/proposals/{id}` with `state` `dismissed`, or `pending` to restore it) changes only the card. An applied one can't be dismissed (`VALIDATION_FAILED`). A proposal that isn't in Claude's message, or a message that isn't this document's, returns `NOT_FOUND`; a sent document's, `VERSION_LOCKED`.
- **A card says where its change is by its immediate parent:** the skill category, role, or project a skill or bullet is under ("Move the skill Alembic in Back End to the end"), or the section for anything placed directly in one, or when the parent is gone. Once it's applied or dismissed, its before and after and reason fold away under a closed "Details" (named for the card for screen readers), leaving its title, its state, and Restore.
- **A proposal waits until the user answers it:** a card stays pending, under its reply, until it's applied or dismissed, however many messages come after. The panel lists every pending card above its message box ("Waiting for you (n)", oldest first, left out with none, and in a sent document's read-only chat), each moving focus to its card.

## Reading an existing resume or cover letter
- **Reading saves nothing:** `POST /api/resumes/read` (or `/api/cover-letters/read`) takes an uploaded file (`file`: its name and its bytes in base64) or pasted text (`text`) and returns what Claude read, each item matched against the library, to fill the review form. A PDF goes to Claude as is; a Word file (.docx) as its text, one paragraph per line. Neither sent returns `VALIDATION_FAILED` (`text`); a file that isn't a PDF or .docx, can't be read, or is over 10 MB, `VALIDATION_FAILED` (`file`); and one Claude finds no resume (or letter) in, `VALIDATION_FAILED` on whichever was sent. The page checks that a file is chosen or text pasted first, and for a base one, that its name is filled in and new (see "Names of resumes and cover letters"), since the name is only saved after the review.
- **The same item is reused, not added again:** an item is the library's when the library (hidden items too) has one of its kind with the same values, ignoring spacing, and for names and titles (sections, skill categories, skills, sign-offs) capitals too, since those are unique that way. Roles match on title, organization, location, and dates; projects on title, affiliation, link, and dates; education on degree, institution, details, and graduation; narrative content and bullets on their text. The review marks the rest "new", and an item changed in the form counts as new unless it's changed back. The match is made again on Save, with what the user corrected.
- **Similar items are the user's choice:** Claude names a library item that looks like the same thing written differently; it's offered only if it's a visible item of the same kind, and not the identical one. "Use the saved one" sends its id (`item_id`) instead of the values, and the item uses that one, with what Claude read under it (its bullets or skills) added under it. Another account's id returns `CROSS_ACCOUNT_LINK` (`item_id`).
- **Every field is checked like the library's own forms:** before Save, the page points to the first required field left empty ("Fill this in, or remove it."), and the backend returns `VALIDATION_FAILED` named for the field that fails. Nothing is saved when anything fails, including the header or sign-off.
- **Listed under their parents:** Save (`POST .../imported`) lists each item, new or reused, last under its section (the built-in "Other" category isn't listed under any), each skill under its category or project, and each bullet under its role or project, unless it's listed there already, and places the tree as read. An item twice in one section, or a section twice, is placed once, where it first comes up.
- **Header and letter parts:** a base one uses the header with exactly the values read (a saved one, or a new one); left empty, the most recently used one. One for a posting uses the posting's header and ignores the one read. A cover letter's sign-off is a saved one with the same text or a new one; a greeting or sign-off left out is a new letter's usual one.
- **Tailored from there:** on a posting, `POST .../imported/tailored` saves it the same way, then has Claude tailor it to the posting starting from it (see "Claude's suggestions"), in one transaction, so if Claude fails (`AI_UNAVAILABLE`) nothing is saved and the review keeps what the user changed. Since Claude starts from the document itself, it isn't based on another one. A base one can't be tailored (`VALIDATION_FAILED`, `job_posting_id`).

## Rewordings
- **Never overwrite library content with a rewording.** When the user accepts a reworded or new bullet point or narrative content, insert a new `bullet_point` or `narrative_content` row and list it under every parent that lists the original (sections, roles, projects), right after the original.
- **Swap it into the current document only.** Point the current resume's or cover letter's join row at the new row. Other resumes and cover letters keep using the original.

## Writing rules
- **Apply every active `writing_rule`** to every suggestion. Find `term` rules in code (whole words, ignoring capitals, a single word's usual endings), then ask Claude whether each match is filler or a real term, and to check `pattern` rules and the tone, in one request (`backend/app/writing_check.py`). Claude's own text is reworded to fix what it finds before it's shown, and the fix is used only if code finds no new filler in it; what's left is flagged with the rule and why. The user's own text is only flagged, never changed. Claude naming a rule that isn't one is left out. The check is built but not yet run: phase 5 step 3's sub-steps 2 to 4 run it on Claude's draft, the chat, and the user's own text (see [BUILD_PLAN.md](BUILD_PLAN.md)); until then the rules reach Claude only in each request's instructions.
- **Apply the resume's or cover letter's tone**, if it has one, to every suggestion for it.
- **Copying a version keeps its `tone_set_id`** unless the user picks another.
- **Writing rules are edited in place:** they steer every suggestion and are never printed, so editing one never saves a new row.
- **Tones change like any other item** (see "Changing an item"), so a sent version keeps the tone it was written with. A tone's dialog edits its name and rules (adding, rewording, removing, and reordering them) in the form, and one Save sends them all: each kept rule with its `tone_rule_id`, new ones without, in order. Rules left out are deleted. A rule id that isn't one of the tone's, or one sent twice, returns `VALIDATION_FAILED` (`rules`).

## Failures outside the database
- **Job posting fetch:** if the page can't be fetched or no job description is found, return `POSTING_FETCH_FAILED` and show the paste-in box. Reading a posting with nothing pasted needs a web address (`http://` or `https://`) in the link field, or it returns `VALIDATION_FAILED` (`url`). Reading saves nothing; the user checks the result and saves the posting.
- **Claude API:** if a request still fails after the SDK's retries, or Claude declines it, return `AI_UNAVAILABLE`. Keep the user's work and offer Retry.

## Timestamps
- `updated_at` defaults to the creation time, and a database trigger updates it whenever a row is edited.
- Join tables have no timestamps. When a resume's or cover letter's selections change (items added, removed, or reordered), update that resume's or cover letter's `updated_at`.
